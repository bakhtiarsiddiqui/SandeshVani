## Baseline and lifecycle findings

- The worktree has substantial pre-existing modified/deleted and untracked
  paths; all are preserved. No staged changes were introduced.
- Access tokens are asymmetric JWTs with configured issuer/audience and a
  persisted `auth_sessions` revocation check. They remain valid only until their
  configured short expiry (default 10 minutes) unless their session is revoked.
- Refresh tokens are high-entropy opaque values (48 bytes), cookie-delivered at
  `/api/v1/auth`, HttpOnly, and persisted only as SHA-256 digests in
  `refresh_tokens`. A login creates one auth session and one UUID family.
- Refresh rotation consumes the presenting token atomically via compare-and-swap
  (`rotated_at IS NULL AND revoked_at IS NULL AND expires_at > now`), issues a new
  token in the same family, and links the ancestor to the descendant via `replaced_by_id`.
- Replay detection triggers immediate and durable family-wide revocation:
  `is_revoked = true`, `revoked_at = now()` across the entire `family_id`, and
  revokes the session via `auth_sessions.revoked_at = now()`. The database transaction
  is explicitly committed before raising HTTP 401 so FastAPI error handlers cannot
  roll back the security revocation.
- Concurrent refresh attempts on the same token are serialized by the atomic
  CAS update: exactly one winner consumes and rotates; losing concurrent requests
  reload the record, observe `rotated_at IS NOT NULL`, and trigger durable replay
  revocation.

## Database Schema (Migration 0003)

Table `refresh_tokens` includes:
- `id` (UUID PK)
- `session_id` (UUID FK -> `auth_sessions.id` ON DELETE CASCADE)
- `token_hash` (VARCHAR(64) UNIQUE, SHA-256 of raw token)
- `family_id` (UUID, indexed)
- `is_revoked` (BOOLEAN, default false)
- `rotated_at` (TIMESTAMPTZ, nullable)
- `revoked_at` (TIMESTAMPTZ, nullable)
- `replaced_by_id` (UUID FK -> `refresh_tokens.id` ON DELETE SET NULL, nullable)
- `created_at` (TIMESTAMPTZ, default now())
- `expires_at` (TIMESTAMPTZ)
