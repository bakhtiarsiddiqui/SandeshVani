## Existing authorization and tenant-context design

- `get_tenant_context` derives the target organization from a JWT active-org
  claim or `X-Organization-ID`, then verifies an active membership server-side
  before exposing the context. A client-supplied ID is not authorization.
- `set_tenant_context` records the organization in `session.info` and, for
  PostgreSQL, uses transaction-local `set_config('app.current_org', ..., true)`.
- Organization routes require permission dependencies for memberships, roles,
  and permissions. Services/repositories additionally filter by organization ID.
- Migration `0001_initial_auth_and_tenancy` enables and forces RLS on
  memberships, membership roles, and roles. Migration `0002_secure_role_permissions`
  adds tenant-safe role-permission schema and forced RLS policies. The policies
  deny organization-owned rows with missing context; platform role/permission
  rows remain deliberately visible.
- The role model includes Organization Administrator, Campaign Manager,
  Communication Team, and Approver organization roles; platform roles are
  separately scoped and cannot be assigned through organization membership APIs.
- No background-task or worker source exists in the current backend.
